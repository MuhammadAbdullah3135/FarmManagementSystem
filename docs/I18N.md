# Internationalization (Phase 7)

Phase 7.1 ships the framework and infrastructure: react-i18next wired into the client, every
client-facing string extracted into bundled English resources, the server-side key mechanism
for validation messages, and a CI guard against new hardcoded strings. It ships **no second
language** — by design, so the plumbing can be proven at zero risk to the English UI.

Phase 7.2 ships the first second language: **Spanish, machine-translated and unreviewed**
(see [The machine-translation flag](#the-machine-translation-flag)). It adds a persisted
locale switcher, locale-aware date and number formatting, message keys for the server's alert
templates, and a coverage guard that fails the build when a locale stops mirroring English.
English output is deliberately unchanged everywhere.

Phase 7.3 ships **Arabic** — the first right-to-left language, and the first that needs more
plural forms than English — and with it the layout work a second script demands: a direction
that reaches the document, antd and dayjs; every physical CSS and inline style replaced by its
logical equivalent; one place that decides which way a directional icon points; and a CI guard
that fails on a new `margin-left` or a fresh `ArrowLeftOutlined`. English output is still
byte-identical, and so is Spanish.

## Architecture

- `client/src/i18n/index.ts` — initialises i18next once. Resources are **statically
  imported JSON**, so there is no HTTP backend and a locale can never fail to load at
  runtime; the worst case is an English string. `initAsync: false` makes the first render
  already translated rather than showing keys for a frame.
- `client/src/i18n/locales/en/<namespace>.json` — one file per feature area
  (`common`, `nav`, `auth`, `dashboard`, `animals`, `breeding`, `feed`, `health`, `hr`,
  `finance`, `inventory`, `tasks`, `reports`, `configuration`, `admin`, `notifications`,
  `offline`, `imports`, `validation`, `errors`).
- `client/src/i18n/serverMessage.ts` — renders server-supplied message keys (below).
- Components use `const { t } = useTranslation('<namespace>')`, so a bare key resolves in
  that file's namespace. The navigation tree instead stores `labelKey: 'nav:x'` and resolves
  it per language, keeping the role-filtered structure language-free.

Adding a string: put the English value in the right namespace file and reference it with
`t('key')`. A missing key falls back to English; a **mistyped** key is caught by the
key-resolution test (`client/src/i18n/i18n.test.ts`), which scans every `t('…')` in source
and asserts it exists.

## Fallback rules

1. Key missing for the active locale → **silent English** (`fallbackLng: 'en'`).
2. Key missing in English too (only possible via a bug) → `parseMissingKeyHandler` renders a
   humanised last segment and logs loudly; the raw dotted key is never shown. The
   key-resolution test makes this unreachable in a shipped build.
3. A locale bundle missing entirely → the English bundle; because resources are bundled, this
   is a build-time impossibility rather than a runtime hazard.
4. A **server** message key this build does not know → the English text the server sent beside
   it (see [Server-generated messages](#server-generated-messages)).

### Arabic is machine-translated too — and its plurals are the part to review first

`locales/translation-status.json` records the same provenance as Spanish (`source`,
`reviewed: false`, date) plus one extra sentence, because Arabic raised a problem Spanish did
not: English says `{{count}} days` and Arabic says it six ways. The forms came from the same
machine translation and were then adapted by hand, which makes them the least-reviewed text in
the bundle. A native reviewer should start there.

What it means for the *guard*, in three rules:

1. **Keys are compared by base name.** `intervalDays_few` is a form of `intervalDays`, so Arabic's
   six keys score 100% of English's one key rather than reporting five strays and one gap.
2. **A plural form may drop `{{count}}`, never add one.** Arabic's dual `يومان` is "two days" with
   no numeral in it, so the placeholder rule is a subset for plural forms and equality for
   everything else — which is still what a renamed `{{count}}` looks like.
3. **A language that carries plural forms must carry every form its own rules select from** —
   read from ICU (`Intl.PluralRules('ar').resolvedOptions().pluralCategories`), not from a
   hand-written table, so the rule cannot drift from the data i18next resolves counts against.
   This is the one that would otherwise go unnoticed: Arabic without `intervalDays_many` still
   *renders*, because i18next falls back to `_other`, so the Arabic for 40 would quietly read
   like the Arabic for 100 and no screen or test would say so. Verified by deleting exactly that
   form: the guard reports `missing-plural-form: health:intervalDays — ar selects zero, one, two,
   few, many, other; no value for intervalDays_many` and fails.

### Direction

The direction of a language is decided in one place — `RTL_LOCALES` in `client/src/i18n/locale.ts`
— and everything else asks it. Adding Farsi, Hebrew or Urdu is a one-line change there.

Three separate mechanisms, because three separate systems decide layout:

- **antd** mirrors its own components from `ConfigProvider direction` (`App.tsx`). It does *not*
  read a `[dir]` attribute, so the prop is not optional.
- **The document** (`documentElement.dir` and `.lang`) is set by `applyDocumentLocale`, for the
  parts CSS owns: scrollbar side, text selection, form controls, default text alignment, and the
  flex order of the `Sider` and the header.
- **dayjs and antd's own locale bundle** (`dayjs.locale('ar')`, `ar_EG`) come from the same
  `App.tsx` effect, which is the one component that re-renders on a language change.

`applyDocumentLocale` also publishes `--fms-fade-direction` (`to left` / `to right`). That looks
like an oddity and is not: a `linear-gradient` direction has no logical keyword in CSS, so a
scroll hint that fades from the edge needs a value that flips with the language. It is the file's
only physical direction, it is allowlisted with that reason, and `rtlRender.test.tsx` asserts it.

### Layout: logical properties, and the three things that are not CSS

Everything a physical direction would break, audited and converted — **16 values**, one in
the stylesheet that is actually imported and fifteen in components:

| What | Was | Now |
|---|---|---|
| `AppLayout.css` scroll hint | `right: 0`, `to left` | `inset-inline-end: 0`, `var(--fms-fade-direction)` |
| Drawer close button, pie-chart legend, quick-select hint, lineage badges, birth tag, nested-row indents | `marginLeft` / `marginRight` / `paddingLeft` / `borderLeft` | `marginInlineStart` / `marginInlineEnd` / `paddingInlineStart` / `borderInlineStart` |
| Audit-log header cells | `textAlign: 'left'` | `textAlign: 'start'` |
| Notification pagination | `textAlign: 'right'` | `textAlign: 'end'` |
| `client/src/App.css`, `client/src/index.css` | 200 lines, imported by nothing since before Phase 1 | **Deleted** |

Three things a `direction` prop cannot fix, each handled where it belongs rather than with a
`[dir='rtl']` override:

1. **Icons whose meaning is a direction.** `i18n/DirectionalIcon.tsx` maps a *role* onto a
glyph: `back` swaps `ArrowLeft` for `ArrowRight`, `enter`/`leave` keep their glyph and are
mirrored with `scaleX(-1)` (which wall the arrow meets is the meaning), and `tree-branch` draws
`↳` or `↲` for a nested configuration row. Five call sites route through it — two back buttons,
check-in, check-out, and the account menu's sign-out — and the guard below fails on a
directional icon anywhere else.
2. **antd's `Drawer` positions itself physically**, so the mobile nav asks `startSide(direction)`
rather than hardcoding `placement="left"`. In Arabic the nav slides in from the right.
3. **Table columns pinned to a side.** The codebase already used `fixed: 'start'` (antd v6 only
pins on that), which the browser mirrors on its own; the guard now fails on `fixed: 'left'`.

### What is deliberately *not* mirrored

Not oversights — each is recorded because someone will otherwise "fix" it:

1. **Charts.** recharts has no RTL support: it draws in a fixed left-to-right coordinate space.
   So the axes, the bars and the line direction stay as they are in Arabic. What *is* localised
   is every label and value inside them, because those go through `format.ts`. Mirroring the
   plots means rewriting them against an RTL-capable charting library or rendering a mirrored
   chart, which is a piece of work on its own and would touch a dozen report pages.
2. **Numeric column alignment.** All 48 `align: 'right'` uses are numeric columns (quantities,
   costs, sizes). Right-alignment there is a property of the *figure*, not of the language:
   digits run left-to-right in Arabic too, so mirroring would move the decimal points away from
   the edge a reader scans. The physical-directions guard counts these and reports the count;
   it does not fail on them.
3. **Server-composed strings** (the export notice's `"1.7 MB"`) and **seeded lookup data** stay
   as they are, for the reasons in 7.2's list below.

### The physical-directions guard

`client/tools/i18n/check-physical-directions.mjs`, run by `npm run lint` next to the other two.
It scans every non-test file under `src/` for a physical direction and names the logical
property to write instead:

- stylesheets — `margin-left`, `padding-right`, `border-left`, a bare `left:`/`right:`,
  `text-align: left|right`, `float: left|right`, a gradient written `to left`/`to right`;
- TSX — the camelCase equivalents, `textAlign: 'left'|'right'`, `fixed: 'left'|'right'`,
  a directional icon outside the helper, and an arrow glyph (`→`, `←`, `↳`) baked into a string;
- counted but not failed — `align: 'left'|'right'`, per the decision above.

The one entry in `tools/i18n/physical-directions-allowlist.json` is the gradient fallback, with
its reason. Like the other guard, the allowlist has to stay honest: an entry with no reason
fails, and an entry that no longer matches anything fails as stale.

What it cannot see: a layout that is *logically* correct but visually wrong in Arabic — an
overlapping label, a truncation, a font that renders Arabic badly. Those need eyes on a real
page, and jsdom has no layout engine, so this is a tripwire for regressions and not a proof.

### The machine-translation flag

Spanish is **not reviewed copy**. That fact is recorded in the repository, not only here:

- `client/src/i18n/locales/translation-status.json` — per locale: `"source":
  "machine-translation"`, `"reviewed": false`, and the date. Read it before treating any
  Spanish string as final.
- `client/src/i18n/locales/README.md` — the same statement, plus the **terminology glossary**
  a reviewer needs (farm → *granja*, tag → *arete*, feed → *alimento*, medicine →
  *medicamento*, and the values deliberately kept in English such as *stock*).

What that means in practice: the Spanish UI is usable and complete, and its wording has never
been read by a native speaker. Sentences that are awkward, over-formal, or regionally wrong
are **expected** and are a review task, not a bug report. Nothing in the test suite can detect
translation quality — only completeness — and the suite does not pretend otherwise.

### The stored language

The choice has two homes, and they answer different questions:

- **The device** (`localStorage`, `fms.locale`) is a hint so the first paint after a reload is
  already translated instead of flashing English while `/auth/me` is in flight.
- **The account** (`User.Locale`, migration `AddUserLocale`) is the durable record, so the
  choice follows the person to another browser or phone. **The account wins when they differ.**

An account that has never chosen adopts the device's language at sign-in
(`reconcileLocaleOnSignIn`), which is what makes a choice made before the server knew about it
stick. An unsupported tag is refused with `validation.locale.unsupported` and leaves the stored
value untouched — silently replacing a Spanish user's preference with English would be the worst
failure mode available here. `LocalePreferenceE2ETests` pins all of it over HTTP: set on one
device, read back by a sign-in from another.

### Formatting (`client/src/i18n/format.ts`)

Two decisions worth stating, because both look like oversights otherwise:

- **English output is unchanged.** `2026-09-24`, `Aug 3, 2026`, `$1,234.57` — byte-identical to
  what the app rendered before, so the diff stays about Spanish and every existing assertion
  keeps meaning what it meant.
- **The currency symbol is untouched.** `formatMoney` prefixes the same bare `$` it always has
  and localises only the number: Spanish gets `$1234,57` and `$43.016,00`, never `1234,57 $`
  or `€`. The farm has no currency setting yet, and inventing a symbol or a position would
  quietly change what a farm's numbers *mean*. Recording a real currency setting is separate
  work.
- Spanish groups thousands only from five digits up (CLDR's `minimumGroupingDigits`), so a
  four-figure amount has no separator in Spanish. That is the locale's own rule, not a bug.

**Behaviour change, called out explicitly:** previously these values went through
`toLocaleString()` with no locale argument, so they followed the **browser's** locale. They now
follow the **app's** language. A Spanish-speaking user on an `en-US` device used to see
`1,234.5`; they now see `1234,5`. `format.test.tsx` asserts exactly that, and `useFormat()`
exists so a component that does not call `useTranslation` still re-renders on a language change
instead of keeping the previous language's dates.

### Alert templates as keys

The server *generates* an alert and a person *reads* it, and those are two different languages.
Rather than pick one, every template is emitted twice: the English text it always carried, plus
a key and raw arguments (`AlertMessageKeys`, stored on `Notification.TitleKey` /
`MessageArgsJson`). The English text is **unchanged and still what the digest email sends** and
what the client falls back to; the key is what lets the notification centre render in the
reader's language months after the condition was computed. Arguments travel unformatted — a date
stays a date, so the reader's language decides how it is written.

Covering the export-ready notice too (`FarmExportJob`) closed the last user-visible notice that
still arrived in English; it is written outside the dispatcher but lands in the same list.

### The locale-coverage guard

`client/tools/i18n/check-locale-coverage.mjs`, run by `npm run lint` alongside the hardcoded-string
checker. Per non-English locale it enforces: the same namespaces, the same keys, no blank values,
every `{{placeholder}}` preserved, and equal line breaks. It also enforces the **allowlist rules**:
a value identical to English is a failure unless it is in
`locales/untranslated-allowlist.json` with a written reason, that entry still *is* identical, and
the list stays under 30 entries. The list has 15 entries today — eleven cognates (*animal*,
*total*, *no*), two unit symbols (`kg`, `x`), the product acronym, *stock* (kept per the
glossary), and the technical `yyyy-MM-dd` pattern. Without that rule, "copy English across and
call it translated" would pass.

What it cannot do: judge quality. An awkward machine translation is a complete translation as far
as a file comparison can tell, which is exactly why the flag above exists.

Its one blind spot in the *other* guard is worth recording: the hardcoded-string checker only
examines template literals in property assignments, so a JSX expression such as
`` `Currently managing: ${farm.name}` `` was never flagged. One such string was found by the
Spanish render test and fixed in 7.2; a JSX template literal is still not covered by CI.

## Server-generated messages

The client renders server messages from a **key plus parameters**, so the server never needs
to know the user's locale.

- `Error` and `FieldError` gained optional `MessageKey` / `MessageArgs`. `Message` is
  **unchanged** — byte-identical to what the create endpoints and both import paths have
  always answered with — so the message-discipline tests from 3.4/4.3/6.1 keep passing.
- The six extracted rules classes (`CustomerRules`, `SupplierRules`, `InventoryItemRules`,
  `EmployeeRules`, `ExpenseRules`, `IncomeRules`) emit keys for their field messages, with a
  length cap passed as an argument (`{ max }`).
- The key reaches the client as an **`X-Message-Key` response header** (see
  `src/FMS.API/ApiMessageKeys.cs`). A header is additive: every existing error body stays
  the exact string it was, and a caller that ignores the header is unaffected. The header is
  listed in the CORS `WithExposedHeaders` because the Pages frontend and the Heroku API are
  different origins.
- `FieldError` keys need no transport at all: they are serialised into the import-preview
  DTO, so the wizard renders them from the same key.
- **Key convention:** a server key is `namespace.path.to.key` (e.g.
  `validation.employee.firstNameMaxLength`). The server has no business knowing i18next's
  `:` separator, so the client splits the first segment off as the namespace and a key whose
  first segment is not a real namespace falls back to English.

### Why email needs its own mechanism

The key-based, client-rendered model cannot cover email: a digest is rendered server-side
and delivered to an inbox that never runs the SPA. Localising email therefore needs a
stored per-user locale and a server-side resource lookup — a different mechanism, deferred to
its own subphase and recorded here so it is not mistaken for an oversight.

## Extraction

A codemod (`client/tools/i18n/extract.mjs`, `npm run i18n:extract`) found and rewrote
user-facing literals: JSX text, user-facing attribute/property values, and
`message.*`/`notification.*` calls. It is a codemod, not a formatter — it replaces only spans
it understood and **reports** what it could not place instead of guessing.

Its guards matter. A string handed to a function, compared with `===`, held in an array, or
assigned to a non-user object property is treated as **data**, not copy (translating a modal
kind or a column source would change behaviour, not language), and a file with a local `t`
binding (a render callback parameter, say) switches the whole file to a `translate` alias
rather than silently shadowing the hook.

What it deliberately left (captured in the CI baseline, see below): module-scope object
literals in a handful of pages, interpolated template literals, and strings containing HTML
entities. The navigation menu, the largest such set, was finished by hand.

## CI guard

`client/tools/i18n/check-hardcoded-strings.mjs`, run by `npm run lint` (and therefore by the
Pages workflow's Lint step), scans `src/pages` and `src/components` for JSX text,
user-facing attribute/property literals, and hardcoded toast messages. It compares against
`hardcoded-strings-baseline.json` and **fails only when the set grows**, so new hardcoded
copy is blocked while the reviewed remainder does not wedge CI. `--update` accepts the current
set after review.

Its limits, stated plainly:

- **False positives:** any literal that is data rather than copy. It cannot tell a domain
  value from a sentence the way the extraction codemod can, which is exactly why the
  remainder is enumerated in the baseline rather than trusted.
- **False negatives:** text that is never a literal — a string assigned to a const and
  rendered later, a sentence built by concatenation, an interpolation a translator would need
  to reorder. Those were found by the codemod's own skipped report instead.

It is a tripping hazard for regressions, not a proof of completeness.

A blind spot of exactly that kind was real, and is now closed: the scanner returned early on a
JSX attribute whose initializer was not a plain string, so a `label:` inside
`items={[{ label: 'Feed Types' }]}` was never seen while the identical literal as a plain
object property was flagged. The scanner now recurses into array and object initializers of
user-facing attributes (with its own fixtures), and the widened scan was reviewed in full:
the option-list labels and the validation and empty-state copy it surfaced are recorded as
reviewed baseline entries or in the remaining-English list below, not silently accepted.

## Remaining English and open items

Deliberately **not** translated in 7.2, and deliberately not silently ignored:

1. **The "X not found" family of server messages is closed; 312 other domain error call sites
   stay English.** Measured rather than estimated: of 561 `Error.*` / `Result<T>.*` factory
   call sites, 249 carry a key and **214 of those were added 2026-10-02** — every site that
   says some form of "… not found". That was the largest single family and the one a reader
   meets most often (a wrong id, a deleted record, a lookup that does not belong to this
   farm), and it was one key per sentence shared across services: `Location not found` is
   answered by Animals, Finance and Inventory from one `validation.lookup.location`.   The remaining sites are **not all missing keys**: about 99 of them pass an already-built
   `Error` straight through (`Failure(validationError)`, `Failure(saved.Error!)`) and inherit
   whatever key that error carries, so they were never work. The real remainder is
   **156 sentences across ~213 sites** — validation rules, conflicts, the import and
   file-upload messages — still plain English with no key, so a Spanish user sees them in
   English. They fall back safely rather than showing a key, which is why this is a gap and
   not a defect — but it is a gap, and it is now a measured one.
   - **Re-measured 2026-10-02, after item 14: 157 sentences across ~209 sites.** The parser
     behind the number changed, not the backlog, and the difference is pass-through calls

## The unkeyed backlog, measured

Before adding more copy, the backlog was measured rather than estimated.
`scripts/i18n-backlog-audit.mjs` walks the four server projects, finds every
`Error.X(...)` / `Result.X(...)` call whose first argument is a string literal with no message
key beside it, and reports the file, line, code and enclosing method of each.

```
node scripts/i18n-backlog-audit.mjs          # human-readable, grouped by file
node scripts/i18n-backlog-audit.mjs --json   # the same rows, machine-readable
```

**Originally 168 unkeyed sites, 126 distinct sentences, and all 168 reachable from a
controller. After the breeding and inventory sweep (item 25) it is 56 sites and 44 distinct, all
56 still reachable.**

The breakdown that matters for sequencing:

| Shape | Sites | Distinct | Why it is its own slice |
| --- | --- | --- | --- |
| `Conflict` / `Superseded` with arguments | 0 | 0 | **Done** — item 17. |
| Other argument-taking (`Validation`, `Unexpected`) | 0 | 0 | **Done** — item 19. |
| `ConfigurationService`'s `InUse` composite | 1 | 1 | Named exemption in the guard; needs plurals and a list joiner. |
| Plain argument-free (`Validation`, `NotFound`, `Unauthorized`, …) | 55 | 38 | **66 done** — items 21, 23, 24 and 25, seven services. The rest is the same shape. |

The remaining 55 plain sites are the largest single block and the cheapest per site: no
arguments, no vocabulary, no server-side formatting. Every argument-taking sentence is now keyed,
which means the two decisions that gated them — raw values on the wire, formatting on the client
— are settled, and the last block needs neither. They concentrate in a few services
(`SpreadsheetReader` 4, `SupplierService` 4, `AttendanceService` 4, `AuthService` 4,
`CustomerService` 3), so it is a per-service sweep rather than a scatter. `FeedService` (17),
`AnimalService` (16), `MedicineService` (9), `VaccineService` (7), `EmployeeService` (7),
`BreedingService` (6) and `InventoryService` (6) are done and have left the guard's
`StillToKey` list, which is down to 21 files.

Three of the ten keys added by the last four sweeps turned out to be sentences another service
already said, which is the argument for sweeping service by service: the reuse is found by
reading the file next to its neighbours, not by looking for it.

One shape inside the remainder is not mechanical after all: eight of the nine `Unauthorized`
sentences are the same sentence with a different verb — *"Only farm owners and managers can
change member roles"*, *…can remove members*, *…can invite members*, and four more. Eight
copies of one sentence is a family, not eight sentences.

Two scripts keep the numbers honest, and both are worth running after any change to the
message surface:

```
node scripts/i18n-backlog-audit.mjs       # what is still unkeyed, and whether a caller can reach it
node scripts/i18n-backlog-audit.mjs --guard   # ...and whether the guard test is watching all of it
node scripts/i18n-verify-english.mjs     # the en bundle renders exactly what the server returns
```

The `--guard` cross-check exists because the backlog was being described twice. The audit
measures it from the source; `ValidationMessageKeyGuardTests` carries a hand-written list of
files it is not yet watching, so that a *new* keyless refusal fails a build while the known
backlog does not. Nothing compared the two, and they had already drifted: `FarmService` and
`FarmExportService` were on the exemption list because they emit unkeyed sentences, but those
sentences are `Unauthorized` and `Unavailable`, which that guard does not claim — so it had
never opened either file and the exemption was decoration. Both are removed.

It reads the guard's regex and its exemption list *out of the C# source* rather than restating
them, because a restated copy is a second thing that can drift from the first. If the C# cannot
be parsed it throws rather than cross-checking nothing, and the ported pattern is proved against
four probe cases before anything is compared with it. The three ways it fails — a hole, a stale
exemption, an unparseable guard — have each been triggered by hand. It runs in CI, in the
`test-client` job beside `verify-phase5.mjs`.

It also prints, per file, what each side counts. They are two independent parsers — the guard's
regex and the audit's argument walker — and they currently agree to the site on all 21 files,
which is worth more than either number alone.

The second exists because a hand-written English string in a bundle is a claim, not evidence. It
reads each call site's arguments out of the server source, renders the bundle entry, and
compares — currently 548 sites and 89 constants, 0 mismatches. It reports its own coverage
because it carried five separate bugs that each checked a subset while printing a clean run
(items 17, 20 and 21): a verifier that says "0 mismatched" without saying how much it looked at is
the failure mode this project keeps meeting.

### What the audit is allowed to be wrong about

Two limits, both stated here so the numbers are not over-trusted:

- **Edges are matched by method name, not by receiver type.** `GetAsync` on two services is one
  node. This over-approximates the graph, and therefore over-approximates reachability — the
  safe direction, since it can only make a sentence look *more* reachable than it is.
- **Dynamic dispatch through an interface is invisible**, for the same reason and the same
  direction.

So "unreachable" is trustworthy and "reachable" is a lower bound. Since nothing came back
unreachable, the bound did not bind.

### Three bugs the audit had before it had an answer

Recorded because each one produced a confident wrong number, which is the failure mode this
project has already paid for twice (Mission 8's `{{max}}` guard, and the nine inline mappings
that shipped green).

1. **Two different method-declaration patterns.** The call graph and the enclosing-method
   lookup were written separately, and the enclosing one could not match
   `public async Task<Result<X>> LoginAsync(` — its return-type alternation stopped at the
   first `>`. Every method with a generic return type resolved to the method *before* it, and
   the audit reported `Invalid email or password` as unreachable. The login failure. Fixed by
   using one shared pattern, and the reason the constant is named `DECL` and commented.
2. **Only dotted calls were edges.** `await ValidateBatchAsync(farmId, items)` has no receiver,
   so every private helper looked like a leaf and `No animals were supplied` — the answer to
   the bulk-animal preview every importer sees — was reported unreachable. Bare calls are now
   edges too, filtered against a reserved-word set.
3. **A bare `"` was required.** The 31 `$"..."` sites were skipped entirely, and those are
   exactly the argument-taking sentences, the ones a reader is most likely to meet in the
   wrong language. This is the bug that would have hidden slice 2b from the audit designed to
   scope it.

The generalisable form, and the third instance of it: *a check that cannot see a whole category
of the thing it checks will report that category as absent rather than as unknown.* Each of
these read as "no such sites exist", which is a much more dangerous shape of wrong than a
count that is merely off.

19. **The argument-taking validation family, done (17 sites, 16 sentences).** The block that
    could not be written before item 17 settled how a value reaches a reader. Three decisions
    came out of it, and the third is a limitation rather than a solution.
    - **Lists go on the wire as arrays and the client joins them with `Intl.ListFormat`.** Four
      sentences (`fileTypeNotAllowed`, `importFieldsUnmapped`, `unknownAlertTypes`, and the one
      medicine case) name several things at once. A server that joined them would have frozen
      English's `", "` into every language; Spanish wants `y` and Arabic `و`, and neither is a
      character the server chooses. This is the same reasoning as sending a number unformatted,
      applied to a string.
    - **An exception's own message is not copy, and the frame around it is.** Four sentences
      carry a CsvHelper, an OpenXML or an AWS message: `importCsvUnreadable`,
      `importWorkbookUnreadable`, `fileStoreFailed`, `fileSignFailed`. Translating the
      diagnostic would invent a sentence the library never sent, so `ARG_KINDS` marks those
      arguments `diagnostic` and renders them as they arrived. A reader who does not read
      English gets the sentence in their language and the machine's words inside it, which is
      the most a system fault can honestly offer.
    - **A free-text unit is not the feed-unit enum.** `Medicine.Unit` and `InventoryItem.Unit`
      are strings a farm typed, while `FeedType.Unit` is the `FeedUnit` enum. Only the latter
      goes through `feed:unit*`; running a medicine's `bottles` through the feed vocabulary
      would translate a farm's own word into a word nobody asked for. The distinction is now a
      `kind` per argument rather than a guess from the argument's name.
    - **A fourth key family, because the first three ran out of homes.** `lookup` means "no
      such record", `conflict` "one already exists", `supersede` "one already answered". None
      of them is what "the file is too large" is, and filing these under `lookup` would have
      claimed a record was missing — a different and wrong thing to tell a reader, and one that
      teaches a translator the group carries no information. `validation` is the fourth family;
      `DomainMessageKeyParityTests` names all four and pins each one's count.
    - **`ARG_KINDS` replaced slice 2b's two ad-hoc key sets**, which had already hit their
      ceiling: adding these sentences meant asking which *key* a new argument belonged to, a
      question about arguments wearing a costume. It is now one table keyed by message key
      then argument name, with a guard test that checks both directions — every placeholder in
      every keyed sentence has a declared kind, and every declared kind appears in its
      sentence. The undeclared case is the quiet one: it renders as the raw wire value, an
      English client is correct, coverage still passes, and only another language sees a value
      nobody formatted.
20. **Two more parser bugs, in the verifier this time.** `i18n-verify-english.mjs` had three
    regexes fail in a row, each silently checking a subset while printing a clean run:
    - **Adjacency.** A pattern requiring the key and its arguments to be adjacent missed every
      site with a comment between them — 25 of 29 covered, reported as a pass.
    - **A comment gap.** Allowing comments in the pattern made it backtrack without bound and
      hang the scan for over a minute.
    - **Escaped quotes.** No regex distinguishes a quote inside `{string.Join(", ", x)}` from
      the quote that ends the literal, so the four list-joining sentences were never checked at
      all and the verifier reported 42 of 46 as clean.
    - The fix is to stop using a regex for this: `readArgs` walks the characters, treating a
      string as opaque and a comment as prose, and it is the same walk the audit performs. The
      verifier's coverage line — `37/37` — is what caught the third of these, and it exists
      for the same reason the guard tests do: a check that reports success for a subset of what
      it claims is worse than no check.
    - The audit had the same class of bug independently: `readArgs` there did not treat a
      string as opaque, so a comma inside a message split it in two. Three "sentences" in its
      output were fragments, and the corrected run moved the backlog from 139 sites to 136.
21. **The argument-free sweep, and the two blind spots it exposed.** 33 sites in `FeedService`
    and `AnimalService` keyed in one pass (item 26 constants, 3 of them found by the new guard
    rather than by the audit). Behind it, `ValidationMessageKeyGuardTests` — the first guard
    that watches the *plain* argument-free shape, with a `StillToKey` ratchet so the list can
    only shrink.
    - **All 122 remaining sites were unguarded.** Measured, not assumed: the lookup guard
      matches only "not found" messages (0 hits on this shape), and the conflict guard only
      its one named `InUse` exemption. So nothing would have failed when the next service was
      left unkeyed.
    - **The guard immediately found 8 sites the audit's backlog had missed** — 7 in import
      services plus `PushSubscriptionService`. A backlog list is a claim about the world; a
      test over the source is evidence.
    - **The verifier could not see any of it.** It skipped calls with fewer than three
      arguments, so all 26 new constants — argument-free by construction — were outside what it
      checked while it printed a clean run. Widening it to two arguments took it from 46 sites
      to 331 and from 37 constants to 63, with 0 mismatches, and it has been proven to fail by
      rewording one bundle value.
    - **The verifier's call pattern had one level of generic.** `<[^<>]*>` cannot match
      `Result<List<FeedingTaskDto>>.Validation(` or `Result<PagedResult<FeedingTaskDto>>`, and
      adding `NotFound` to the method alternation brought the 64 lookup keys into scope for the
      first time. The audit had already been fixed for exactly this shape and the verifier had
      not — the same bug living in two scripts at once.
22. **The guard and the backlog were two hand-written descriptions of one list.** The audit
    measured the unkeyed backlog from the source; the guard exempted a list typed out by hand.
    Nothing compared them, and they had drifted in the direction that reads as coverage — see
    `node scripts/i18n-backlog-audit.mjs --guard`, which now runs in CI.
    - **The drift was two stale entries**, `FarmService` and `FarmExportService`, listed for
      unkeyed sentences the guard does not claim. Both removed.
    - **The first version of the cross-check was itself the bug it exists to catch.** It
      compared the guard's exemption list against *all seven* factories the audit reports, so
      it flagged `ConfigurationService` — whose only unkeyed site is the `Conflict` composite
      already exempted by name in the *conflict* guard. A cross-check that fails on a category
      it does not cover trains people to ignore it. It now scopes holes to `Validation` and
      `Failure`, and reports the 17 sites no guard watches as a number rather than a failure.
    - **`Singleline` was not doing what its comment claimed.** The guard's comment said the
      option is what lets `\s*` span the newline; `\s` matches a newline in both engines without
      it, and the option only affects `.`, which the pattern does not contain. What actually
      makes the guard work is scanning the file as one string. This mattered because the
      JavaScript port "needed" the equivalent flag and would have carried the same wrong
      reasoning into a second place; the port now proves itself against probe cases instead.
23. **The health sweep, and a sentence three services share.** `MedicineService` (9) and
    `VaccineService` (7) keyed in one pass, for ten new keys rather than sixteen — “Quantity
    must be greater than zero” is said by the feed services, the inventory services and the
    medicine service, and it reuses `QuantityMustBePositive` rather than becoming a third
    translation to keep in step. The three passes have now keyed 49 sites with 32 keys.
    - **Two delete refusals that sound alike were deliberately kept apart**: “Cannot delete
      medicine with existing usage records”, “Cannot delete stock batch with existing usage
      records”, and “Cannot delete vaccine type with existing …” differ in *what* is in the
      way. Folding them into one key with an argument for the noun would have been tidier and
      would have made the obstacle an interchangeable slot, which is exactly the kind of
      generalisation that costs a translator the specifics.
    - **The Arabic was checked against the project's existing terms rather than translated
      fresh**: `دفعة` for a stock batch, `جدول` for a schedule, `لا يمكن حذف … لديه …` for the
      delete refusals, all taken from strings already shipped in the bundle. A first draft used
      `تشغيلة` for “batch” and had a stray non-Arabic character in one value; both were caught
      by grepping the new values for characters outside the Arabic block before writing the
      file, which is cheaper than a translator finding them later.
24. **The employee sweep, and a guard that was wrong on its first run.** `EmployeeService`'s
    seven sites keyed with six new keys; the seventh reuses `FromDateAfterToDate`, which
    FeedService keyed first. That leaves 38 argument-free keys over 55 sites.
    - **The Arabic character check rejected digits.** The guard was "no character outside the
      Arabic block", and it fired on `500 حرفًا` — correct Arabic, and a string that has shipped
      in this bundle for months. The check was widened to Arabic letters, decimal digits and
      whitespace. Worth recording because the check's *first* run in the previous sweep caught
      a real typo, which is exactly why a second false positive could have led to it being
      deleted rather than fixed.
    - **“Amount must be greater than zero” is now in the bundle three times** —
      `expense.amountPositive`, `income.amountPositive`, and the new `salaryAmountPositive`.
      The first two are client-side form validations and have no server constant, so this is
      not a mistake to be deduplicated away: each namespace carries its own copy by design, and
      the sentence needed a server key to exist before the client could ever render it. The
      constant says so.
    - **A dead map that had never worked.** `i18n-verify-english.mjs` read every constant's
      doc comment into `ENGLISH_BY_KEY` and then never read the map. Wiring it up meant fixing
      two bugs before it could say anything: it looked for `/**` in a file written with `///`,
      so it found no comment at all; and when it looked for the last `///` it missed every
      wrapped summary, because the last `///` of a five-line comment is its `/// </summary>` and
      the sentence sits above that. Every one of the 172 constants was reported as having no
      documented English. It now checks all 172 against the bundle, reconciling the three
      differences that are not disagreements — `{detail}` against `{{detail}}`, curly against
      straight quotes, and a sentence wrapped in a comment and not in a bundle — and has been
      proven to fail by rewording a doc comment alone. The claim "the exact English this API has
      always answered" is now a checked claim rather than a comment.
25. **The breeding and inventory sweep, and a guard that was wrong twice.** Twelve sites across
    the two services keyed with ten new keys; `InventoryService` reused `MovementDateFuture` from
    the feed sweep, the third reuse in four sweeps. 68 argument-free keys now cover 66 sites.
    - **The Arabic character guard was rewritten twice before it was right.** Its first version
      rejected digits, its second rejected punctuation and fired on the colon in
      `إحدى: يوم، أسبوع، شهر` — a string this bundle has shipped for months. What it was
      actually for is stray *letters*, so that is now the rule: a non-Arabic letter fails,
      digits and punctuation do not. It is proven on both sides — a CJK character and a slipped
      Latin word are caught, while `500 حرفًا` and the colon sentence pass.
    - **The four movement types are an existing vocabulary.** `Purchase, Consumption, Transfer,
      or Adjustment` is baked into the English of `MovementTypeFilterInvalid`, and the same four
      values already exist as `enums.json`'s `movementType` keys in all three locales. The
      translations were taken from there rather than coined. A follow-up worth taking: the
      sentence could take its values as an `enum:MovementType` argument and be joined by the
      client, which would remove a list currently edited in five places whenever a fifth
      movement type is added. Not done here, because the English is frozen and adding an
      argument changes the wire format.
    - **Two sentences about one fact stayed two keys.** `MovementTypeInvalid` says
      “Invalid movement type” and `MovementTypeFilterInvalid` names the alternatives. A key may
      not acquire words the API never sent, so the pair cannot be merged.

## The next milestone (7.4)

The next one is **the remaining 55 argument-free `Validation`/`NotFound`/`Unauthorized` sites**.
Nothing about them needs a decision: no arguments, no vocabulary, no list, no server-side
formatting — the same shape slice 2a did 29 of, slice 2b 21 more of, and the argument-free
sweeps 33, then 16, 7 and 12. They are concentrated in a few services (`SpreadsheetReader` 4,
`SupplierService` 4, `AttendanceService` 4, `AuthService` 4, `CustomerService` 3), which makes it
a per-service sweep rather than a scatter. Each service leaves the guard's `StillToKey` list as
it goes, and the cross-check fails if one is left behind.

One shape in the tail is not mechanical: the seven import services each say the same sentence
about an empty sheet, so it is one sentence said seven times and wants one key across all of
them.

Two things sit behind that one. The eight `Unauthorized` sentences are one sentence said eight
times — *"Only farm owners and managers can…"* — so they want one slice that treats them as a
family rather than eight copies, which is the first argument-free shape that needs a decision
about how a verb is carried. And `AuthService`'s `Invalid email or password` is the most visible
English left in the product: it is the first thing a wrong password ever puts on screen.

And the six sentences that interpolate an exception's own message are keyed but only partly
translated, by choice (item 19): the frame is the reader's language and the diagnostic inside it
is not. That is defensible for a farm app, and it is a decision worth revisiting rather than
inheriting — the alternative is dropping the diagnostic from the localised sentence entirely,
which loses the one clue a support conversation starts from.

The sentence after that — `ConfigurationService`'s `Cannot delete {entityLabel} '{name}': still
used by {usedBy}. {remedy}` — is not a key. It needs structured data, i18next plurals and a
translated list joiner, and it is the one piece of this family that is a design task rather than
a copy task.

After that, **server-side resource lookup**, so the remaining domain messages and the digest
email render in the account's stored language. `User.Locale`, the key convention, the
`X-Message-Key`/`X-Message-Args` transport and a client renderer all exist, so this is resources
and a renderer rather than plumbing.

Two candidates sit behind those. **Currency as a real setting**: `formatMoney` still prefixes a
bare `$` in every language, which is the largest remaining thing a farm could call wrong about
a number. And smaller, **Arabic copy review**, which is a translator's task rather than a
build's, and needs the same review Spanish is waiting for.

## Plugging in another language

1. Add `locales/<lang>/` (copy the English files as the starting point). If the language has
   more plural categories than English (Polish, Russian, Czech…), expand each `{{count}}` key
   into that language's forms — `untranslated-allowlist.json` and the coverage guard already
   understand them.
2. Register it in `client/src/i18n/index.ts` and add it to `SUPPORTED_LOCALES` (client) and
   `SupportedLocales` (server).
3. Add the antd bundle to `ANTD_LOCALES` in `client/src/App.tsx` and import the dayjs locale.
4. If it is right-to-left, add it to `RTL_LOCALES` in `client/src/i18n/locale.ts`. The document
   attribute, antd's direction, the nav drawer and the directional icons all read from there;
   the physical-directions guard then covers every page automatically.
5. Run `npm run lint`: the coverage guard fails until every English key exists in the new
   locale, and fails again for any value left identical to English without a reason. The
   physical-directions guard fails on layout that would not mirror.
6. Record the translation's provenance in `locales/translation-status.json` — reviewed or not.
7. Run the device pass in `docs/VERIFICATION.md` (§8) if the language is right-to-left: jsdom
   cannot tell you whether the page *looks* right, only that it renders.
